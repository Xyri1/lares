# DECISIONS — Lares

**Artifact:** DECISIONS · **Project:** Lares (`lar`) · **Status:** Living · **Date:** 2026-07-24

Each row records a fork taken among real alternatives: what was chosen, what was rejected, why, and status. Status vocabulary: **decided** — explicitly approved by the maintainer; **proposed** — recommendation on the table, not yet approved; **open** — gated on an external result (spike, license read, availability check). Nothing carries *decided* without explicit approval. IDs are chronological and permanent; rows are grouped by topic, so IDs are not monotonic within the document (D24/D25 live in Stack & Platform, before D16). Cross-cutting invariants live in PRINCIPLES; contracts in SPEC; sequencing in ROADMAP. Rows mutate when reality drifts.

## Product & Positioning

**D01 — Parametric emotion over state-machine animation.** *Chosen:* continuous, history-dependent affect driving rig parameters. *Rejected:* discrete event→clip mapping (the entire incumbent field: Codex native pets, clawd-on-desk, agentpet, OpenPets, petdex). *Rationale:* emotion is a richer, pre-attentively readable encoding of agent status; history-dependence is the one behavior state machines cannot produce and therefore the defensible differentiator. *Status:* decided.

**D02 — Agent-generic, cross-vendor positioning.** *Chosen:* "your AI's companion," watching any harness. *Rejected:* coding-agent-only framing. *Rationale:* harnesses are pivoting to everyday tasks (ChatGPT desktop Work mode, Claude Cowork, WorkBuddy); platform vendors will ship native status affordances, so the defensible ground is vendor-neutrality. *Status:* decided.

**D03 — v1 non-goals fence.** *Chosen:* no permission bubbles, no gamification, no marketplace, no observer-LLM mode, no VRM, no pet chat, no telemetry. *Rationale per refusal:* permission UI is clawd's mature turf and a large surface; gamification is agentpet's identity; marketplace precedes supply; observer mode drags privacy design into MVP; VRM belongs to phase 2; chat converts a status companion into a different product; telemetry contradicts the local-only principle for negligible insight. *Status:* decided; fence revisions require a new row.

**D04 — Free OSS with a phase-2 commercial horizon.** *Chosen:* Lares itself is free and complete, never gated; a potential paid VRM character-creation service monetizes character identity continuity later. *Rejected:* monetizing the pet; hiding the phase-2 intent. *Rationale:* OSS communities accept paid assets/services around a free tool but punish bait; the model is stated openly. Phase 2 constrains v1 only through identity portability (D08). *Status:* decided.

**D28 — Emotion gate binds the public launch, not the alpha.** *Chosen:* v1 alpha ships at the best passing rung of the M2 retreat ladder — (a) continuous trend curves, (b) exaggerated/body-weighted mapping, (c) history-through-cues (affect drives cue selection, blend weight, transition speed, idle texture) — while P8's release-blocking history-dependence criterion applies to the public (M5) release. Tuning discipline: engine physics (decay, mood EMA, saturation) frozen against unit tests early; subjective iteration confined to the affect→parameter mapping layer; rung pacing and drops owner-judged — the two-week timebox and weekly cadence struck 2026-07-27 (solo project, no calendar pressure; M2b blocks nothing but itself and M1b interleaves); forced-choice A/B recordings at default Lar size stay normative, parameter deltas diagnostic. *Rejected:* holding the alpha for the full gate (an aesthetic gate with no objective finish line is the schedule's biggest black hole; every rung remains P8-compliant because expression stays a function of accumulated affect history, never of the latest event alone). *Status:* decided (timebox struck 2026-07-27 by the maintainer).

## Architecture

**D05 — First-person emotion (mode 1 first).** *Chosen:* the agent reports its own affect via the emote protocol; hooks provide baseline state. *Rejected for v1:* observer-LLM appraisal (deferred, dual-mode later); transcript reading (privacy surface, cost, latency). *Rationale:* the agent already holds full context — appraisal piggybacks on tokens the user pays for, nothing leaves the machine, and the pet becomes the agent's face rather than an observer's guess. *Status:* decided.

**D06 — LLM is the appraiser, never the animator.** *Chosen:* semantic judgment enters as sparse events; deterministic dynamics own every rendered frame. *Rejected:* LLM-generated animation curves or per-frame LLM involvement. *Rationale:* responsiveness, cost, debuggability; the render loop must never wait on inference. *Status:* decided.

**D07 — Two-timescale affect model.** *Chosen:* continuous (valence, arousal) with fast emotion dynamics plus a slow mood layer. *Rejected:* single-timescale state; discrete emotion enums as the internal representation. *Rationale:* two clocks produce both reactive beats and temporal texture (tired idle vs. fresh idle); exact dynamics belong to SPEC. *Status:* decided.

**D08 — Renderer-agnostic character package with identity portability.** *Chosen:* manifest = model reference + tag→parameter/motion mapping + idle modulation + persona metadata, renderer-neutral by contract. *Rejected:* Cubism-shaped package format. *Rationale:* preserves the one-soul-many-vessels path (2D desktop body now, 3D bodies later) and keeps the open thing — the format — independent of the proprietary renderer. *Status:* decided.

**D09 — Emote protocol: cue-first, freeform fallback, temporal control.** *Chosen:* the agent selects from the character's available cues when one fits (tags with optional clamped intensity; tag→affect mapping lives in the character package, where personality-as-config attaches); when none fit, it emits a freeform expression — an ad-hoc parameter composition applied ephemerally, clamped to the model's parameter ranges. The agent also controls timing: per-expression duration (capped) and an expression queue (depth-capped, engine-preemptible on higher-priority events), enabling small performed sequences. The engine owns all blending and transitions regardless of source (continuity criterion holds). *Rejected:* closed-vocabulary-only protocol (starves agent expressiveness in exactly the semantic moments the product exists for); raw affect floats as the primary interface (agents pick reliably from labeled sets, emit calibrated numbers unreliably — floats survive only inside freeform payloads under clamps). *Rationale:* mirrors the D25 ladder at runtime — prefer authored assets, degrade to composition; exact caps, queue semantics, and preemption rules are SPEC content. *Status:* decided (as amended by the maintainer).

**D10 — Dual ingress, one schema.** *Chosen:* an MCP tool surface plus a plain local HTTP event route over one versioned schema; hooks reach the event route via the app's bundled embedded-Node forwarder (D14), and any agent that can shell out can hit the same route with any local HTTP client. *Rejected:* MCP-only (hooks execute commands by definition and many harnesses lack MCP); output-stream sentinel codes (pollutes user-visible output). *Rationale:* "anything that can run a command can emote" is what kills the adapter treadmill. *Status:* decided.

**D11 — Single aggregating Lar in v1.** *Chosen:* one Lar resolving all tracked sessions to highest-priority state. *Rejected for v1:* one Lar per session / multiple concurrent Lares (post-v1; the Lar/Lares grammar anticipates it). *Rationale:* scope. *Status:* decided.

**D26 — Emote adoption: MCP instructions primary, hooks-only floor.** *Chosen:* the daemon's MCP server `instructions` field carries the emote guidance (Context7 pattern: crisp triggers and anti-triggers — emote at meaningful beats: session start, state change, third consecutive failure, recovery, completion; never per tool call); tool descriptions double as triggers; per-harness skill/instruction files are reinforcement only. Hooks-only is the official product floor: all PRD §9 emotion criteria must pass with zero agent emotes, and the worst-case idle/working/done degeneracy (the native-pet baseline) is accepted for alpha, improvable later. *Rejected:* skill files as the primary vector (weakest placement — per-harness, opt-in, invisible to future harnesses). *Rationale:* Context7's observed ~80% well-timed invocation comes from placement (instructions ride server registration into every context automatically) plus engineered trigger vocabulary; the one non-transferable ingredient is task-instrumentality — emoting never helps the agent finish — which is exactly why the floor must hold without emotes. *Status:* decided.

**D27 — No auth on the loopback ingress.** *Chosen:* the server binds `127.0.0.1` with no token; browser-origin attacks are stopped by rejecting any request bearing an `Origin` header and requiring `Content-Type: application/json` (forces a failing CORS preflight); `runtime.json` carries only `{version, port, pid}` — no secret, so file permissions are a don't-care. *Rejected:* per-run bearer token (the original scheme — strands every live agent session on app restart because static MCP configs can't follow a rotating token, adds config re-sync plumbing in two harnesses, and stops no attacker the Origin check doesn't: any local process running as the user could read the token file anyway); per-install token (less churn, same non-threat). *Rationale:* on a loopback port the real adversary is browser JS, not local processes; Origin rejection addresses exactly that at zero operational cost, and daemon-restart recovery (S9) works again — stable URL, nothing stale. *Status:* decided.

**D31 — Brain/body split: the performance feed is the seam.** *Chosen:* the main process (brain — sessions, affect engine, emote protocol, packages) contains no renderer knowledge; the overlay (body) subscribes to a renderer-neutral performance feed — affect vector, mood, baseline state, cue-level expression stack, motion beats — and translates it for its renderer (cue→asset resolution and idle-motion synthesis are body-side). Knob data (freeform emotes, expression authoring) crosses the feed as opaque name+number pairs validated against the inventory the body reports; the brain never interprets knob meaning. One body in v1; a future 3D body attaches at the same feed. *Known limitation:* freeform compositions are body-specific by nature (knob names come from the loaded model); mitigation is `status()` reporting the active body, richer mode feedback deferred. *Rejected:* routing/translation inside the renderer process (buries the contract inside Electron — a native/Unity-class 3D vessel would attach at the process boundary, not below it); banning knob traffic from the brain entirely (would relocate freeform and authoring into the body for no v1 gain). *Rationale:* the channel already exists as the IPC payload; declaring it the contract costs a rule, not a layer — P6 keeps its single-implementation discipline while 3D expansion becomes a plug-in instead of a rewrite. *Status:* decided.

## Stack & Platform

**D12 — Live2D first, behind the D08 seam.** *Chosen:* Live2D Cubism as the sole v1 renderer (pixi-live2d-display runtime). *Rejected:* VRM-first (open stack and VRoid self-serve creation are real advantages, but 2D model supply, the rigger economy, illustration aesthetic, and founder ecosystem access win the opening move; VRM is the designated second backend and phase-2 substrate); Inochi2D (ideologically aligned, ecosystem too small, immature web runtime); Spine (per-app runtime licensing hostile to open source); Rive (strong state-machine tech, no character ecosystem). *Rationale:* the pet is only as alive as its available characters; 2D assets are dirt cheap and abundant. *Status:* decided.

**D13 — Shell: Electron.** *Chosen:* Electron — frameless transparent window, `setIgnoreMouseEvents(true, {forward: true})` for click-through with a live hit-test loop. *Rejected:* Tauri (no shipped Live2D overlay exists on it; click-through requires manual host-side cursor polling with reported input-smoothness concerns on Windows; the footprint advantage doesn't outweigh unproven shell ergonomics for the category-defining window behavior); fully native (per-OS Cubism Native SDK work, forfeits cross-platform — AgentPet's macOS-only stance shows the cost). *Rationale:* every shipped Live2D desktop overlay in the wild (Open-LLM-VTuber pet mode, hime-display, git2968/Desktop-pet, chiikawa-pets) is Electron; the proven path was chosen explicitly. Known Electron care items inherited from field evidence: no white init flash (create hidden, show after first paint), screen-edge clipping and spawn positioning (Codex's overlay bugs), premultiplied-alpha fringing check on both OSes. *Status:* decided.

**D14 — Daemon is the app; the app hosts the MCP server; hooks run the app's embedded Node.** *Chosen:* the Electron main process is the daemon — session table, affect engine (pure TS module, headless-testable), character package, overlay — and hosts a loopback-bound local HTTP server: a streamable-HTTP MCP endpoint plus a plain event route. Server lifecycle mirrors app lifecycle by construction (Blender MCP / Unity MCP pattern): app running ⇒ MCP up; app closed ⇒ connection refused, doubling as a presence signal. The MCP surface also carries D25's authoring loop (read parameter inventory, preview an expression on the live character, save). Baseline-state hooks run Lares' own executable in embedded-Node mode (`ELECTRON_RUN_AS_NODE`) executing a bundled forwarder script — reads the app-written discovery file (endpoint discovery, the OpenPets pattern; no token — D27), pipes the hook's stdin JSON to the event route, exits; zero external dependencies, single-language TypeScript, one mechanism on every OS (the clawd pattern, field-proven at scale). Simulate is an in-app scenario player plus a repo dev script; package validation is the app's import check plus a dev script. *Rejected:* bare `curl` hooks (saves imperceptible milliseconds against multi-second tool round-trips while adding an external dependency and token-config plumbing; zero shipped pets use it); compiled Rust helper (legitimate field pattern — AgentPet ships one — but its only offer, fast standalone execution without deps, is now delivered by a binary we already ship; deferring is cheaply reversible since Lares owns and re-syncs the hook command lines); stdio MCP shim; standalone headless daemon; npx/bunx-style hook packages (slowest cold start, ecosystem dependency). Rust stays out of v1 with the door explicitly unlocked. *SPEC items:* discovery file location, loopback binding with browser-origin rejection (no auth — D27), fixed default port with override. *Status:* decided.

**D15 — v1 harness set: Claude Code + Codex.** *Chosen:* Claude Code command hooks; Codex via its official plugin surface — a Lares plugin bundling the hook set (PermissionRequest, SubagentStart/Stop et al.) plus the MCP entry, distributed through a GitHub-hosted marketplace and installed through Codex's own trust flow (skills are reinforcement only, deferred beyond M5a). *Amended 2026-07-27 (005-D5):* the `~/.codex/sessions/` JSONL fallback is deleted, not deferred — Codex's hooks engine went official and stable, and push-only sensing (P11) bars reading harness-owned files; if a harness's hooks are unreliable, that harness is unsupported, not worked around. Tripwire for reconsidering: real users blocked by enterprise `requirements.toml` marketplace allowlisting. *Amended 2026-07-28 (M3b live smoke):* Codex discovers, surfaces, and trust-reviews plugin-bundled hooks but never executes them — execution sat behind a `plugin_hooks` feature flag (openai/codex#19705) that current builds report as removed with the value pinned false; the runtime treats the key as unknown if set. Verified on desktop-bundled 0.146.0-alpha.3.1 and standalone 0.134.0: all eight hooks trusted, zero dispatches logged, while the plugin's MCP entry connects and emotes work. Consequence: the plugin delivers MCP (skills later); Codex baseline states are undeliverable through the plugin today. Design-around (next slice): the app writes user-level `~/.codex/hooks.json` — which runs under the stable `hooks` feature — with the Claude Code writer discipline (content-recognition, idempotent re-sync, parse-abort, backup-once, atomic), Codex's `/hooks` trust review still gating execution. Tripwire to fold hooks back into the plugin and delete the writer: Codex ships plugin-hook execution. *Amended 2026-07-29 (slice 009):* Claude Code joins the official-plugin surface — `plugins/claude-code/` in the same repo-hosted marketplace (root `.claude-plugin/marketplace.json`, `/plugin marketplace add Xyri1/lares`), and because Claude Code *executes* plugin hooks the plugin delivers hooks + MCP both; the settings/`~/.claude.json` writer is demoted to a launch-time legacy cleaner (009-D1/D2). Same day, the maintainer's re-smoke resolved the docs-vs-live contradiction the migration surfaced: current Codex builds *do* execute plugin-bundled hooks after trust review — the fold-back tripwire fired. Hooks fold back into the plugin (the committed `hooks/hooks.json` was already the single source of truth — 006-D2 made this a deletion, not a migration); the `~/.codex/hooks.json` writer is deleted, its removal pass retained as launch-time legacy cleanup and uninstall (mirroring 009-D2). Both harnesses now deliver hooks + MCP through their plugins, with app-side writers reduced to legacy cleaners. *Rejected:* guiding users to enable a hidden, removed feature flag (not an install path). *Rejected for v1:* Cursor, Gemini, opencode, and the long tail (community-contributable via the protocol); ChatGPT Chat/Work modes (no hook surface exists — unsupported under P11, not worked around). *Rationale:* two deep integrations prove the protocol; breadth is the ecosystem's job. *Amended 2026-07-30:* both plugins ship the same harness-neutral `emoting` skill — reinforcement of the D26 instructions, emote-only (D32, 009-D3 as amended). *Status:* decided; amended 2026-07-27, 2026-07-28, 2026-07-29, 2026-07-30 (skill timing, Claude Code plugin — slice 009, then Codex fold-back executed on the fired tripwire, then both plugin skills); Work-mode surface tracked.

**D24 — Webview Live2D runtime; Cubism 3/4 only.** *Chosen:* pixi-live2d-display remains the v1 runtime behind the D31 body seam. Lares accepts VTube Studio-style `.model3.json` packages whose MOC reports the official SDK 3.0, 3.3, 4.0, or 4.2 runtime value. Cubism 2.1 is outside the model ecosystem Lares targets and is rejected; Cubism 5 MOC version 5 or later is rejected before model revival. Editor 5-authored assets exported for SDK 4.2 remain accepted. *Rejected:* shipping the dependency's separate Cubism 2 stack merely because it exists; adopting the Cubism 5 fork; migrating to the official SDK on the first Cubism 5 model; extension- or JSON-version-based guessing. *Rationale:* VTube Studio is the target ecosystem and the public model supply is predominantly Cubism 3/4; the narrower claim avoids a second legacy format family and known Cubism 5 compatibility risk. Maintainer additionally weights the community implementation's code quality and API design above the official SDK's. *Status:* decided; amended 2026-07-30 (010-D1/D2).

**D25 — Expression sourcing: supplied assets first, agent-authored second, raw params last.** *Chosen:* import unions indexed and recursively discovered `.exp3.json`/`.motion3.json` assets and never assumes that either set is prevalent (`sdd/research/live2d-model-distribution.md`, 2026-07-29). Each valid supplied asset is callable under its artist name with a null affect coordinate; filenames, directories, VTS hotkeys, and `.vtube.json` never assign emotional meaning. Calibration explicitly adds affect coordinates. Missing cues use slice 007's authoring loop — inventory → dedicated live preview → conversational user acceptance → save/update — and hand-written raw parameters remain the escape hatch. Imported expressions retain Add/Multiply/Overwrite behavior. Models with sparse calibrated sets degrade gracefully: autonomous selection uses the nearest mapped cue while null-coordinate cues remain agent-emote-able. *Rationale:* this preserves drop-use asset compatibility without pretending every VTS customization is an emotion. Agent-authored `.exp3.json` is the tractable hatch-equivalent for Live2D; generation is setup-time local authoring, never frame-time (D06). *Status:* decided; research wording corrected 2026-07-29 and compatibility boundary amended 2026-07-30 (010-D3/D4/D8).

## Identity & Licensing

**D16 — Name: Lares; unit: a Lar.** *Rejected with cause of death:* Daimon (AI-sidecar runtime and crypto agent network own the word in-space), Anima (design-to-code SaaS owns dev-tool mindshare), Tama (tama96 virtual pet, TAMA-MCP squats the CLI, Rust AI server), Wisp (phonetic collision with Wispr in AI tooling; describes formless light, not a character), Yorishiro/Numen/Fylgja/Duende (lost on catchiness). *Rationale:* guardian-household-spirit meaning; singular/plural grammar maps to single/multi-agent natively; one-syllable daily-use form. *Status:* decided.

**D17 — Domain lares.io; org lares-sh; crate `lar` reserved.** *Rejected:* larez.ai (misspelled variant bleeds traffic to the stranger owning lares.ai, worse for consumer audiences); lares.sh-as-primary (dev-only signal; retained as secondary/redirect); .ai generally (unavailable in correct spelling; reserved as an option for a separately-branded phase-2 product). npm: dropped entirely — nothing publishes to npm (D30), so the unscoped `lares` squat and all scope questions are moot. Crate and Homebrew reservations dropped as moot — no CLI binary ships (D14). No GitHub org: the repository lives on the founder's personal account (org lares-sh proposal dropped). *Status:* decided.

**D18 — Source license: Apache-2.0.** *Rejected:* MIT (no patent grant; Lares ships a protocol and format intended for third-party and commercial adoption); AGPL (poisons the funnel — commercial products won't embed the format, and ecosystem adoption is the strategy). Competitor code (clawd, AGPL) is untouchable either way; all implementation is clean-room. *Status:* decided.

**D19 — Asset licensing is per-character, split from code.** *Chosen:* bundle only a model with explicitly reviewed redistribution terms, exact artifact, license text, required notice, and any separately licensed media; official Live2D samples follow the Free Material License plus per-character terms, and commissioned assets must grant redistribution rights up front. Akari remains excluded (test-stream-only terms). *M0 clearance (2026-07-25):* Hiyori is the cleared fallback; her terms and notice are recorded in `sdd/clearances/M0-clearances.md`. *M5a amendment (2026-07-29):* the bundled default is a build selection, not Hiyori product identity, and replacements require the same written clearance before packaging. *Slice 010 amendment (2026-07-30):* Haru is the intended default because her loose expressions exercise the generic VTS path; Hiyori remains a regression fixture. Haru's additive clearance is recorded in `sdd/clearances/M0-clearances.md`; voice files and source/editor files are excluded, and the curated model3 omits optional motion `Sound` entries (with the runtime strip retained as defense in depth). This does not reopen M0 or authorize another sample. *Status:* decided; sealed for Hiyori and voice-free Haru.

**D20 — Cubism Core distribution mechanics.** *Chosen:* bundled Core with license notice. Basis (read 2026-07-25, quotes in `sdd/clearances/M0-clearances.md`): Proprietary Software License §5.1 grants copying/distributing Redistributable Code as part of Derivative Works; §2.2 exempts General Users / Small-Scale Enterprises from the Publication License Agreement and fee. §6.8 forbids releasing the Core under a non-Live2D license, so the Core is never committed to the Apache-2.0 repo — the build/package step fetches it from Live2D's official distribution; the installer ships it with notice. *Rejected:* user-loaded external Core (worse first run, no compliance gain). *M1a verification:* confirm `live2dcubismcore` in the pulled SDK's `RedistributableFiles.txt`; read the Open Software License when pixi-live2d-display's vendored Cubism Framework lands. *Status:* decided; sealed (M0).

## Ecosystem & Operations

**D21 — No telemetry; GitHub-proxy metrics; disclosed update check.** *Chosen:* no telemetry of any kind; a disclosed update check against GitHub releases is the only app-owned outbound request. No formal success gates, phase-2 tripwires, or kill criteria are adopted for v1 — measurement is deliberately deferred; GitHub-side signals (stars, release downloads) remain passively available if ever wanted. *Amended 2026-07-30 (008-D9):* an explicit **Configure Agent Integrations…** click may invoke the harness-owned plugin managers to perform P3's permitted user-initiated public marketplace download; Lares itself adds no HTTP client or background network path for setup. *Rationale:* local-only is a principle, not a feature. *Status:* decided (as amended by the maintainer).

**D22 — Bilingual from day one; GitHub Releases only at launch.** *Chosen:* en + zh-CN README and docs at launch, neither language preferred over the other. *Amended 2026-07-29:* bilingual extends to the app UI — all user-visible strings (tray, dialogs, notifications, calibration status) ship en + zh-CN from a typecheck-enforced const string table in `src/main/strings.ts`; no i18n dependency, parity is a compile error. Language follows the system locale (Hans variants → zh-CN; Hant variants → en, wrong-variant Chinese being worse than English) with a persisted tray override. Agent-facing text (clipboard calibration prompt, MCP/protocol strings) and logs stay English; installer strings localize with M5b packaging. *Amended 2026-07-30:* the launch-channel deferral is resolved: the GitHub Release page is the sole public launch channel, with no HN/X/Rednote launch push in v1. *Rejected:* i18next/framework (two locales, ~50 strings, one process — the dependency buys plural rules and loaders nothing here needs; revisit at a third locale or community translators); a multi-channel launch campaign. *Status:* decided (as amended by the maintainer).

**D23 — v1 demo on free models, no commissioned flagship.** *Chosen:* Haru carries the launch demo once D19's additive clearance closes; Hiyori remains a regression fixture (D19/010-D7). *Rejected:* pre-launch flagship commission (reversal of an earlier working assumption). *Rationale:* speed to proof; commission money and weeks are better spent after the parametric thesis demonstrates pull. *Status:* decided; amended 2026-07-30.

**D29 — Silent adapter registration in v1 alpha.** *Chosen:* the Claude Code adapter auto-registers its managed settings block (hooks + MCP entry) on app launch with no consent UI; the Codex side is user-run and guided — marketplace add + `/plugins` install, gated by Codex's own trust flow (005-D4) — so Lares ships no consent UI for it either. *Rejected for alpha:* per-harness Connect/Disconnect onboarding (YAGNI now; deferred). *Context for the revisit:* research confirmed Claude Code imposes no trust prompt on user-level hooks — they load silently at next session start — so Lares' own UI is the only consent gate that can ever exist there, and the dotfile-auditing audience arrives at public launch. *Amended 2026-07-29 (009-D1):* the Claude Code half is superseded — registration moves to the user-run marketplace plugin, gated by Claude Code's own plugin install/trust surface, so the consent-UX revisit for Claude Code is resolved by the harness itself; the app's only remaining silent write on that side is the legacy cleanup pass removing what older builds registered. Baseline sensing on Claude Code is therefore opt-in behind the install — accepted for channel parity with Codex. Codex posture unchanged. *Amended 2026-07-30 (008-D9):* **Configure Agent Integrations…** is now Lares's explicit initial consent surface. Only after confirmation, Lares invokes a compatible harness-owned plugin manager with fixed mutation arguments and post-verifies exact marketplace/plugin identity. Codex discovery spans standalone launchers and its macOS/Windows desktop-bundled manager, exact JSON capability probes continue past missing or outdated candidates, and App/CLI surfaces sharing the same Codex home see the same install. Direct executables remain shell-free; package-manager discovery or launch may use a fixed OS shell command containing only Lares-owned literals, never interpolated external input. Lares never edits harness configuration directly, calls Codex app-server's under-development plugin mutation methods, installs at startup, or bypasses Codex's `/hooks` trust review; existing sessions remain unchanged. *Status:* decided; silent registration superseded by plugin delivery plus explicit tray setup, with App/CLI manager discovery amended 2026-07-30.

**D30 — Native-installer distribution; npm dropped.** *Chosen final path:* intentionally unsigned macOS and Windows native installers attached to GitHub Releases — the sole public distribution channel — plus a one-line install script: `curl | sh` on macOS and a PowerShell `irm | iex` equivalent on Windows. Public releases retain `-unsigned` artifact names, publish SHA-256 checksums, and document the exact Gatekeeper/SmartScreen bypasses. Everything ships inside the app: the forwarder is bundled (D14), dev scripts live in-repo, and the character package schema publishes as docs (R7) — npm carries no payload. *Staging amended 2026-07-29:* M5a manually builds the unsigned installers, validates clean-machine installation with the documented bypasses, and tests install-script logic against local fixtures only. *Amended 2026-07-30:* M5b adds GitHub Actions publication, public Release assets and checksums, and production one-line URLs; Apple signing/notarization and Windows code-signing are excluded unless the maintainer revisits this policy. A semantic `package.json` version increase pushed to `master` is the sole automatic release signal: corrections and decreases skip packaging, while an explicit manual run may publish the current `master` version. After tests and both native package inspections pass, CI creates `v<version>` at that commit and publishes the Release. *Rejected:* npm-published packages; paid platform signing for v1; tag-driven or path-inference release triggers; presenting unsigned artifacts without explicit disclosure and bypass instructions. *Rationale:* a desktop app deserves one install story, but the maintainer accepts OS warning friction rather than recurring signing costs; GitHub release provenance and published checksums aid verification but do not suppress Gatekeeper or SmartScreen. A semantic increase is less ambiguous than inferring release intent from changed paths, and manual dispatch covers deliberate corrections without pretending they are bumps. *Status:* decided (distribution policy amended by the maintainer).

**D32 — Calibration is pull-only; the tray arms it (lands M5a).** *Chosen:* agents never hear about character-setup work unsolicited — the MCP `instructions` stay emote-only, and the mapping/authoring flow is user-initiated (in M4, a docs prompt block; slice 007). At M5a the tray surfaces package state as a status dot — red: no cues calibrated, yellow: partial, none: fully calibrated; the dot means "the engine can't auto-select the vocabulary yet," never breakage, since uncalibrated cues stay agent-emote-able with a zero nudge (007-D3) — plus a "Map expressions…" item that arms a daemon flag: while armed, *new* sessions' MCP instructions carry a one-line calibration invite; the flag disarms on completion or re-toggle, and arming copies a kickoff prompt to the clipboard for the session already open. *Rejected:* auto-initiated calibration after import (intrusive — hijacks agent sessions into interviews the user never requested; the maintainer's objection at the 007 grilling); skill-file-only discoverability (invisible, and consent should live Lares-side). *Rationale:* Lares cannot start an agent conversation — agents call in — so the only honest daemon-side initiation is a consent flag agents read at connect; placement mirrors D29's trajectory (the daemon, not the agent, decides when setup is offered). *Status:* decided 2026-07-28 by the maintainer; implementation lands with the M5a tray.

**D33 — Managed character library under Electron user data.** *Chosen:* installed Lares owns copied packages under `app.getPath("userData")/characters`; first run seeds the build-selected cleared default only when the library is empty, upgrades never overwrite it, and imports/switches commit only after validation plus successful body load. Same-named packages coexist with numbered UI labels; no `lares/1` ID field is added. *Rejected:* external live references (path/removable-media drift); source-tree runtime storage (not writable or stable after installation); overwrite-on-upgrade (destroys authored work); hardcoding the bundled character's identity. *Rationale:* one managed root makes installed assets durable and uninstall scope explicit while preserving P5 portability. *Status:* decided 2026-07-29 by the maintainer.
